# 多模态生成工作台 —— 后端实现详解

本文档逐项讲解后端三类核心能力（文生文、文生图、图片理解）的具体 API 使用、业务编排逻辑与代码细节。

## 1. 总体架构

后端采用「分层 + 模型适配」设计，核心思路是**业务层只依赖抽象接口，不耦合具体模型 SDK**：

```
HTTP 接口层 (app/api/routes.py)
      │
      ▼
业务编排层 (app/services/generation_service.py)   ← 创建任务、后台线程执行、状态流转
      │
      ▼
模型适配层 (app/providers/)                        ← 抽象接口 + DashScope 具体实现
      │
      ▼
阿里云百炼 DashScope SDK（通义千问 / 万相 / 千问 VL）
```

关键分层职责：

| 层 | 文件 | 职责 |
|----|------|------|
| HTTP 接口层 | [routes.py](app/api/routes.py) | 接收请求、参数校验、SSE 推送 |
| 业务编排层 | [generation_service.py](app/services/generation_service.py) | 创建任务、后台线程、状态流转、结果落库 |
| 事件总线 | [event_bus.py](app/services/event_bus.py) | 进程内任务事件分发，驱动 SSE |
| 模型适配层 | [base.py](app/providers/base.py) + [dashscope_provider.py](app/providers/dashscope_provider.py) | 统一抽象 + 具体模型调用 |
| 数据层 | [models.py](app/models.py) + `SQLite` | 生成历史持久化 |

---

## 2. 一次生成的完整生命周期

无论哪种能力，都走同一条链路：

```
POST /api/generate
   │
   ├─ 1. 校验 mode 与必填参数
   ├─ 2. 图生文时：把 base64 图片保存为本地文件
   ├─ 3. 在 SQLite 插入一条记录（status = pending）
   ├─ 4. 启动一个后台线程执行真正的模型调用
   └─ 5. 立即返回 task_id 给前端

后台线程（generation_service._run）
   ├─ 把 status 更新为 running
   ├─ 调用 provider 对应方法
   │     ├─ 文生文：流式逐段产出 → 实时推送 SSE delta
   │     ├─ 文生图：异步提交 + 轮询 → 下载图片到本地
   │     └─ 图生文：上传识别 → 返回结果文本
   ├─ 成功：status = done，结果落库，推送 done 事件
   └─ 失败：status = error，错误落库，推送 error 事件

前端通过 GET /api/tasks/{id}/stream（SSE）实时接收进度与结果
```

这条链路的好处：**前端拿到的永远只是 task_id，慢任务不阻塞请求**。下面逐个拆解三种能力在 provider 层的具体 API 调用。

## 3. 文生文（text → text）

### 3.1 使用的模型与 SDK

- 模型：`qwen-plus`（通义千问 Plus）
- SDK 类：`dashscope.Generation`
- 特点：支持流式输出，配合 `incremental_output` 返回真正的增量片段

### 3.2 代码实现

文件位置：[dashscope_provider.py](app/providers/dashscope_provider.py#L27-L42)

```python
def generate_text(self, prompt: str) -> Generator[str, None, None]:
    """流式生成文本。"""
    responses = Generation.call(
        model=self.TEXT_MODEL,          # "qwen-plus"
        messages=[{"role": "user", "content": prompt}],
        result_format="message",        # 以 message 结构返回
        stream=True,                    # 开启流式
        incremental_output=True,        # 返回增量片段（关键参数）
    )
    for response in responses:
        if response.status_code == HTTPStatus.OK:
            chunk = response.output.choices[0].message.content
            if chunk:
                yield chunk
        else:
            raise RuntimeError(f"文生文调用失败: {response.code} {response.message}")
```

### 3.3 逐项细节说明

**`stream=True`**：让 SDK 返回一个可迭代的生成器，每拿到一段就 yield 一次，而不是等完整结果。

**`incremental_output=True`（关键）**：
- 这是本项目踩过的一个坑。DashScope 的 `Generation.call` 在 `stream=True` 且 `result_format="message"` 时，默认返回的是**从开头到当前位置的累积文本**，而非增量。
- 如果不加这个参数，把每段拼接起来会造成严重重复（例如「你好你好！很高兴…」）。
- 设置为 `True` 后，`message.content` 变成真正的增量片段，线性拼接即得到完整正确文本。

**返回类型是生成器**：`generate_text` 声明返回 `Generator[str, None, None]`，调用方通过 `for chunk in ...` 逐段消费。这契合业务层的流式推送逻辑。

**错误处理**：`status_code != HTTPStatus.OK` 时抛出 `RuntimeError`，携带 `response.code` 与 `response.message`，最终会被业务层捕获并记为 error。

**流式消费在业务层的落地**（[generation_service.py](app/services/generation_service.py#L62-L70)）：

```python
def _run_text(self, db, record, prompt):
    parts = []
    for chunk in self._provider.generate_text(prompt):
        parts.append(chunk)                                   # 累积到内存
        event_bus.publish(record.id, {"type": "delta", "text": chunk})  # 实时推给前端
    record.result_text = "".join(parts)                       # 结束后一次性落库
    record.status = "done"
    db.commit()
    event_bus.publish(record.id, {"type": "done", "result_text": record.result_text})
```

设计取舍：流式过程中**只推送 SSE 不写库**，全部完成后才一次性 `commit`，避免每个 token 都触发数据库压力。

## 4. 文生图（text → image）

### 4.1 使用的模型与 SDK

- 模型：`wanx-v1`（通义万相）
- SDK 类：`dashscope.ImageSynthesis`
- 特点：图片生成耗时长，DashScope 采用**异步任务**模式：先提交拿 task_id，再轮询查询结果

### 4.2 代码实现

文件位置：[dashscope_provider.py](app/providers/dashscope_provider.py#L44-L64)

```python
def text_to_image(self, prompt: str) -> str:
    """文生图：异步提交任务并轮询，成功后下载图片到本地目录。"""
    rsp = ImageSynthesis.async_call(
        model=self.IMAGE_MODEL,   # "wanx-v1"
        prompt=prompt,
        n=1,                      # 生成 1 张
        size="1024*1024",         # 输出尺寸
    )
    if rsp.status_code != HTTPStatus.OK:
        raise RuntimeError(f"文生图提交失败: {rsp.code} {rsp.message}")

    task_id = rsp.output.task_id
    while True:
        result = ImageSynthesis.fetch(task=task_id)
        status = result.output.task_status
        if status == "SUCCEEDED":
            url = result.output.results[0].url       # 云上临时图片 URL（有效期 24h）
            return self._download_image(url)
        if status in ("FAILED", "CANCELED"):
            raise RuntimeError(f"文生图任务失败: {result.output.code} {result.output.message}")
        time.sleep(2)                                # 轮询间隔
```

### 4.3 逐项细节说明

**两段式调用（提交 + 轮询）**：
1. `async_call` 提交任务，仅返回 `task_id`，不阻塞等待出图。
2. `fetch(task=task_id)` 反复查询，`task_status` 有 `PENDING / RUNNING / SUCCEEDED / FAILED / CANCELED` 等状态。

**轮询循环**：每 2 秒查一次，直到 `SUCCEEDED`（取图）或 `FAILED/CANCELED`（抛错）。图片模型通常需要数十秒，轮询是标准做法。

**为什么下载到本地**：`results[0].url` 是百炼返回的临时 URL（有效期仅 24 小时）。个人本地工具要保证历史记录长期可看，所以立即下载到本地磁盘。

**下载实现**（[dashscope_provider.py](app/providers/dashscope_provider.py#L91-L98)）：

```python
@staticmethod
def _download_image(url: str) -> str:
    os.makedirs(config.OUTPUT_DIR, exist_ok=True)
    filename = f"{uuid.uuid4().hex}.png"
    local_path = os.path.join(config.OUTPUT_DIR, filename)
    urllib.request.urlretrieve(url, local_path)
    return local_path
```

用 `uuid4().hex` 生成唯一文件名，避免覆盖。

**业务层落地**（[generation_service.py](app/services/generation_service.py#L72-L78)）：

```python
def _run_image(self, db, record, prompt):
    local_path = self._provider.text_to_image(prompt)
    filename = os.path.basename(local_path)
    record.result_url = f"/outputs/{filename}"   # 转成前端可访问的相对路径
    record.status = "done"
    db.commit()
    event_bus.publish(record.id, {"type": "done", "result_url": record.result_url})
```

关键点：把**本地绝对路径**转为**前端可访问的相对路径** `/outputs/{filename}`。这个路径由 FastAPI 的 `StaticFiles` 挂载提供（见 [main.py](app/main.py)），前端 `<img src="/outputs/xxx.png">` 即可直接展示。

## 5. 图片理解（image → text，即图生文）

### 5.1 使用的模型与 SDK

- 模型：`qwen-vl-plus`（通义千问 VL）
- SDK 类：`dashscope.MultiModalConversation`
- 特点：多模态输入，content 数组里同时放图片和文本；SDK 支持 `file://` 本地路径自动上传

### 5.2 代码实现

文件位置：[dashscope_provider.py](app/providers/dashscope_provider.py#L66-L80)

```python
def image_to_text(self, image_local_path: str, prompt: str) -> str:
    """图生文：SDK 会自动上传本地文件并解析。"""
    messages = [
        {
            "role": "user",
            "content": [
                {"image": f"file://{image_local_path}"},   # 本地图片绝对路径
                {"text": prompt},                          # 针对图片的问题
            ],
        }
    ]
    response = MultiModalConversation.call(model=self.VL_MODEL, messages=messages)
    if response.status_code == HTTPStatus.OK:
        return self._extract_vl_text(response.output.choices[0].message.content)
    raise RuntimeError(f"图生文调用失败: {response.code} {response.message}")
```

### 5.3 逐项细节说明

**`file://` 本地路径自动上传**：
- 这是本项目简化的关键。百炼多模态模型要求图片传 URL，但 DashScope SDK 支持 `file://{绝对路径}` 形式，会**自动把本地文件上传到临时存储再传给模型**，无需手动处理 OSS 上传凭证。
- 因此业务侧只需把前端图片保存到本地目录、拿到绝对路径即可。

**多模态 content 结构**：`content` 是一个数组，元素用 key 区分类型——`{"image": "..."}` 表示图片，`{"text": "..."}` 表示文本。多张图/多段文字可并列。

**返回内容可能是列表**：千问 VL 的 `message.content` 在不同模型版本下可能是 `str`，也可能是分段列表（如 `[{"text": "..."}]`），所以写了归一化方法 `_extract_vl_text`：

```python
@staticmethod
def _extract_vl_text(content) -> str:
    """千问 VL 的 content 可能是字符串也可能是分段列表。"""
    if isinstance(content, str):
        return content
    if isinstance(content, list):
        return "".join(item.get("text", "") for item in content if isinstance(item, dict))
    return str(content)
```

这不是兜底逻辑，而是对同一接口返回结构差异做正确解析。

### 5.4 图片从哪来 —— base64 保存链路

图生文需要先有本地图片，图片来自前端上传的 base64。处理逻辑在 [routes.py](app/api/routes.py#L118-L127)：

```python
def _save_base64_image(data_url: str) -> str:
    """把前端传来的 base64 data URL 保存为本地文件，返回绝对路径。"""
    if "," in data_url:
        data_url = data_url.split(",", 1)[1]   # 去掉 "data:image/png;base64," 前缀
    raw = base64.b64decode(data_url)
    os.makedirs(config.UPLOAD_DIR, exist_ok=True)
    path = os.path.join(config.UPLOAD_DIR, f"{uuid.uuid4().hex}.png")
    with open(path, "wb") as f:
        f.write(raw)
    return path
```

前端先把图片转成 data URL（`FileReader.readAsDataURL`）随请求提交，后端解码写盘即可，避免了 multipart 文件上传的复杂度。

## 6. 任务编排层 GenerationService

文件位置：[generation_service.py](app/services/generation_service.py)

这一层是「模型的抽象能力」与「HTTP 接口」之间的桥梁，负责把一次生成变成可追踪、可异步执行、可推送进度的任务。

### 6.1 create_task —— 建任务 + 起线程

```python
def create_task(self, mode, prompt, image_local_path=None) -> int:
    db = SessionLocal()
    record = GenerationRecord(mode=mode, prompt=prompt, status="pending")
    db.add(record)
    db.commit()
    task_id = record.id       # 拿到自增主键作为 task_id
    db.close()

    thread = threading.Thread(
        target=self._run,
        args=(task_id, mode, prompt, image_local_path),
        daemon=True,          # 守护线程，随主进程退出
    )
    thread.start()
    return task_id
```

- 先落库拿自增 `id`（这就是 task_id），再启动后台线程，最后返回 id。
- 用 `threading.Thread` + `daemon=True`，契合「个人本地工具」的低并发场景，避免了引入 Celery/Redis 的复杂度。

### 6.2 _run —— 状态流转与异常兜底

```python
def _run(self, task_id, mode, prompt, image_local_path):
    db = SessionLocal()
    record = db.get(GenerationRecord, task_id)
    record.status = "running"
    db.commit()

    try:
        if mode == "text":
            self._run_text(db, record, prompt)
        elif mode == "image":
            self._run_image(db, record, prompt)
        elif mode == "image_to_text":
            self._run_image_to_text(db, record, image_local_path or "", prompt)
    except Exception as exc:
        record.status = "error"
        record.error = str(exc)
        db.commit()
        event_bus.publish(task_id, {"type": "error", "error": str(exc)})
    finally:
        db.close()
```

- 统一状态机：`pending → running → done / error`。
- **异常统一在这里捕获**：三个 `_run_*` 方法各自干净地写业务，任何抛错都会被记入 `record.error` 并推 `error` 事件，前端能看到失败原因。

### 6.3 三个 _run_* 方法对比

| 方法 | provider 调用 | 结果字段 | SSE 事件 |
|------|--------------|---------|----------|
| `_run_text` | `generate_text()` 流式 | `result_text` | 逐段 `delta` → 最终 `done` |
| `_run_image` | `text_to_image()` 同步等轮询 | `result_url` | 仅 `done` |
| `_run_image_to_text` | `image_to_text()` | `result_text` | 仅 `done` |

三者共同点：成功后都是「更新状态为 done → 提交数据库 → 推送 done 事件」。

## 7. SSE 事件流

### 7.1 EventBus 事件总线

文件位置：[event_bus.py](app/services/event_bus.py)

```python
class EventBus:
    def __init__(self):
        self._queues = {}                     # {task_id: queue.Queue}

    def subscribe(self, task_id):              # SSE 连接建立时调用
        return self._queues.setdefault(task_id, queue.Queue())

    def publish(self, task_id, event):         # 后台线程调用
        q = self._queues.get(task_id)
        if q is not None:
            q.put(event)

    def unsubscribe(self, task_id):            # SSE 连接断开时调用
        self._queues.pop(task_id, None)
```

- 本质是内存里的 `dict + 阻塞队列`：每个 task_id 对应一个 `queue.Queue`。
- 后台线程 `publish` 往队列塞事件；SSE 生成器 `get` 阻塞取事件。
- 进程内、无第三方依赖，适合单机本地工具。

### 7.2 SSE 生成器

文件位置：[routes.py](app/api/routes.py#L81-L111)

```python
def _sse_generator(task_id):
    q = event_bus.subscribe(task_id)
    try:
        # 先补发当前状态，避免任务已完成导致事件丢失
        db = SessionLocal()
        record = db.get(GenerationRecord, task_id)
        if record is not None:
            if record.status == "done":
                yield _sse({"type": "done", "result_text": record.result_text, "result_url": record.result_url})
                return
            if record.status == "error":
                yield _sse({"type": "error", "error": record.error})
                return
            yield _sse({"type": "status", "status": record.status})
        db.close()

        while True:
            try:
                event = q.get(timeout=15)
            except queue.Empty:
                yield ": keep-alive\n\n"      # 15 秒无事件就发心跳，防止连接被中断
                continue
            yield _sse(event)
            if event.get("type") in ("done", "error"):
                break                          # 终态后结束 SSE
    finally:
        event_bus.unsubscribe(task_id)
```

两个关键设计：
1. **补发逻辑**：SSE 连接建立时先查一次数据库。若任务已经完成/失败，直接补发终态事件，避免「任务太快、前端还没连上就丢结果」。
2. **心跳**：`queue.get(timeout=15)` 超时后发送 `: keep-alive` SSE 注释行，防止长时间无事件时连接被代理/浏览器强制断开。

### 7.3 事件类型约定

| 事件 type | 载荷字段 | 触发时机 |
|-----------|---------|---------|
| `status` | `status` | SSE 建立时补发当前状态 |
| `delta` | `text` | 文生文流式过程中的每个片段 |
| `done` | `result_text` / `result_url` | 生成成功 |
| `error` | `error` | 生成失败 |

前端只需 switch 这四种事件类型即可（见 [frontend/src/api.ts](../frontend/src/api.ts) 的 `StreamEvent` 类型）。

## 10. 关键设计点总结

1. **模型适配层**：业务层只认 `BaseProvider` 三个抽象方法，将来换模型（本地 Qwen-VL、OpenAI 等）只需新增一个 provider 类，不改业务编排与 HTTP 层。

2. **统一异步任务模型**：三种能力都走「建任务 → 后台线程 → 状态流转」，前端只需要「提交拿 id + 订阅 SSE」一套交互。

3. **SSE 双保险**：连接建立时先补发当前状态，配合运行期队列推送，杜绝竞态丢结果。

4. **图片本地化**：文生图结果下载到本地、图生文上传图保存到本地，保证个人本地工具的历史记录长期可用、不依赖云上临时 URL。

5. **增量参数是坑**：文生文流式必须 `incremental_output=True`，否则拿到的是累积文本导致重复。
